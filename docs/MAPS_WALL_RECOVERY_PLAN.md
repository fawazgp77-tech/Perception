# Maps reliability and wall-response implementation plan

Scope: improve the v5.1 camera + Mappls build. Preserve the existing CameraX obstacle pipeline and camera-first speech policy. Do not depend on ARCore or change the separate depth mode in this work.

## Findings from the current code

- `MainActivity` already declares and requests camera plus fine/coarse location at startup, but the app does not show a distinct location-permission state or explain whether the permission was already granted, denied, approximate-only, or device Location is off. Test a fresh install as well as an update; an already granted permission will not show a new Android prompt.
- `PreciseLocationTracker` uses raw GPS/network providers and route start rejects fixes older than 15 seconds or less accurate than 30 m. That can produce “location unavailable” despite permission being granted, especially indoors or while a first fix is pending. Guidance later requires 25 m; these thresholds need separate treatment.
- Destination entry calls one-result geocoding and routes immediately from that first result. There is no suggestion list or explicit place selection. Search and routing failures are collapsed into one message, hiding permission, connectivity, entitlement, no-result, and no-walking-route cases.
- `InAppWalkingMap` is present and draws a route after route confirmation. Because the route must succeed before it appears, the current map failure looks like “no map.” The MapView's runtime authorization, style/tile loading, lifecycle, and route overlay must be checked on a physical phone.
- The normal camera runs scene segmentation no faster than every 650 ms. `PathPolicy` requires a central wall label or wall-plus-ending-floor; an unlabeled, uniformly plain view is intentionally treated as unknown. Existing unit tests explicitly encode that behavior.

## Workstream A — make maps functional and diagnosable

1. **Reproduce on the target phone before changing thresholds.** Record app version, Android version, precise/approximate permission state, whether system Location is on, whether coordinates and accuracy appear, network state, and the *category/code* of each Mappls search, routing, and map error. Do not log addresses, raw coordinates, license files, or tokens. Confirm the installed APK's application ID and signing-certificate fingerprint match the Mappls Console registration, and that search, autosuggest, maps, and walking routing are provisioned with quota available. Run separate smoke calls for suggestion, selected-place lookup, walking route, and map tiles. This establishes whether failures are device location, credentials/entitlement, or route coverage.
2. **Repair permission and location onboarding.** Keep a single camera + fine/coarse permission request on first launch, then show separate, accessible states for camera, precise location, approximate-only, denied/permanently denied, device Location off, acquiring fix, and ready. Resume location acquisition after returning from Settings. Use Android's location-settings check and an explicit “Try current location again” action. Do not request location repeatedly after permanent denial. Camera assistance must remain available when location is unavailable.
3. **Improve fix acquisition without faking precision.** Prefer a one-shot current fix followed by foreground updates using the fused provider where available; retain an Android `LocationManager` fallback for phones without Google Play services. A recent coarse/less-accurate fix can populate the map and origin preview with its accuracy shown, while walking turn speech waits for an appropriate fix. Make “waiting for GPS” nonblocking so users can search a destination before the fix arrives. Derive a route-start threshold from field data instead of hardcoding 30 m; never label a broad fix “pinpoint.”
4. **Add place suggestions.** Add Mappls Place Autocomplete or Autosuggest to destination entry, debounced around 300–500 ms and biased around the current location when available. Show 5–8 results with place name, full address, and city; support keyboard, TalkBack, and spoken destination input. After a spoken query, show the same candidates and require the user to select one. Store the chosen Mappls place ID/coordinates and display the exact selected destination before routing. A free-typed address must be resolved and explicitly selected, not silently take the first geocode result. Verify the account's autocomplete entitlement and quota.
5. **Separate route and service errors.** Search states: no matches, network unavailable, Mappls authentication/configuration error, service not enabled/quota reached, and retryable server error. Routing states: no pedestrian route, invalid destination, service/auth failure, timeout, and connection failure. Preserve the real error category in non-sensitive diagnostic logs and show a specific next action in the UI. Never switch to a driving route or imply walking coverage where none was returned.
6. **Show an actual in-app map earlier.** Put a Mappls map preview on the destination/route-confirmation screen even before guidance starts, with user-location marker only when available. After route success, fit the map camera to both origin and destination and draw the full pedestrian polyline. In navigation, keep the existing small map over the camera and the half-screen expansion; keep the user marker and route visible on resize and resume. Show a clear map-loading/error state if tile authorization or loading fails. Use the selected place and route coordinates, not a re-geocoded string, through confirmation and navigation.
7. **Keep camera first.** Preserve obstacle speech/vibration priority; route cues should wait or repeat when suppressed, and should stop when location becomes stale, inaccurate, or the app is paused. Avoid using map routing to declare crossings or roads safe. Validate map rendering and CameraX simultaneously for heat, frame rate, and screen-reader usability.

## Workstream B — faster possible-wall warning

1. **Measure current model behavior first.** Capture consented test clips/screenshots on the target phone for a close plain wall, textured wall, open corridor, blank sky, covered/partially covered lens, overexposed frame, dim room, floor at different camera pitches, doorway, glass, and pavement. Annotate first-warning latency, model wall/floor fractions, camera-quality state, and false alerts. Keep this data local; no user imagery or location in logs.
2. **Add a separate `possible obstruction ahead` state.** When a fresh frame shows little or no connected walkable floor in the central lower field, plus evidence of a broad, near, low-texture surface or a path that visibly terminates, issue a cautious warning quickly. Use existing angle/occlusion/lighting checks to reject unusable views. A uniform image by itself is **not** proof of a wall; do not call it a wall or announce a clear side without positive corridor evidence.
3. **Tune latency on real hardware.** Profile capture, resize, 512×512 model inference, object detection, and speech-start time. Reuse image conversion where possible and avoid extra allocations; keep `STRATEGY_KEEP_ONLY_LATEST` and the analysis worker. Test a shorter segmentation interval only if measured processing remains below frame budget. Let strong evidence warn on one fresh result, while weak evidence needs a second fresh result. Do not count a cached result twice.
4. **Protect directional guidance.** Only suggest left/right when a connected floor/sidewalk region supports that side and the object detector does not flag a nearby obstacle there. Otherwise say “Possible obstruction ahead; stop and check” once, then wait for the user to turn. Add hysteresis and warning cooldown so repeated frames do not spam speech.

## Validation and release gates

- JVM tests: permission/location state transitions; fix age/accuracy and provider fallback; debounced suggestions and stale-response cancellation; selection-to-route coordinate integrity; distinct Mappls errors; map view state across expand/collapse/resume; path-state hysteresis, cached-frame handling, and ambiguous blank/occluded views.
- Build gates: `testDebugUnitTest`, `assembleDebug`, and `lintDebug` pass. Inspect packaged permissions and Mappls assets without exposing secrets.
- Phone matrix: fresh install and upgrade; Android 12+ precise versus approximate; denied/permanently denied; device Location off/on; indoors then outdoors; data off/on; valid and ambiguous India POIs; unreachable pedestrian destination; map mini/half-screen while camera analysis runs. Use a sighted helper in a controlled area for obstacle testing.
- Success criteria: permission state is understandable on first launch; no “location unavailable” when a usable fresh fix is present; search shows selectable alternatives; each failure explains its category; route and moving marker render inside the app; camera warnings remain dominant; a close plain wall triggers a cautious warning within the measured target agreed after baseline tests, without treating covered lenses or open corridors as walls. No release claim of “pinpoint” location, universal wall detection, or guaranteed safe arrival.

## Delivery order

1. Diagnose Mappls entitlement/signing and target-phone location failures.
2. Fix onboarding/current-location acquisition and add granular errors.
3. Add suggestions, explicit selection, confirmation, and always-visible map preview.
4. Verify live route rendering and camera/map coexistence on a phone.
5. Collect wall examples, implement cautious fast obstruction state, tune and retest.
